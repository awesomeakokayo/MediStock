# MediStock Backend Implementation Guide

**Product:** MediStock  
**Backend framework:** Python + FastAPI  
**Document status:** Planned backend specification; implementation has not started unless a later implementation record says otherwise.  
**Audience:** Backend engineers, frontend engineers, technical lead, QA and coding agents.  
**Authority:** This document defines the proposed backend boundary. The root `PRD.md` remains the product source of truth for product goals, workflows, demo limitations and frontend contracts.

---

## 1. Purpose and boundary

The hackathon frontend is local-first and uses browser persistence. The backend described here is the next implementation phase. It is being documented now so the frontend can be designed against stable API and domain concepts.

**Do not implement this backend as part of the 48-hour frontend-only demo unless the project lead explicitly changes the scope.** No production backend, cloud database, live integrations, authentication service or remote AI call should be added to the local demo.

The backend will become the authoritative multi-user, multi-organisation system for:
- Identity, organisations, facilities, locations and permissions.
- Product catalogue, suppliers and procurement/receiving records.
- Batch-controlled consumable stock and auditable stock movements.
- Reusable equipment asset lifecycle.
- Aggregated service/diagnosis category analytics where lawfully supplied.
- Reporting, forecasts and explainable recommendations.
- Controlled inter-facility resource requests and transfers.
- Audit, notifications, imports, exports and integration adapters.

## 2. Backend principles

1. **Ledger before mutable totals.** Stock balances are derived from validated stock movements or maintained as transactionally consistent projections. Never silently overwrite quantity.
2. **Tenant isolation by construction.** Every tenant-owned query and write is scoped to an organisation and authorised facility on the server.
3. **Explicit semantics.** Receipt, internal issue, consumption, return, wastage, expiry, adjustment and external transfer are different event types.
4. **Traceability.** Batch/lot, expiry, location, actor, timestamp, reason and source reference are recorded where relevant.
5. **No clinical decision-making.** MediStock is operational resource intelligence, not a diagnosis, prescribing or treatment system.
6. **Human approval for consequential actions.** Procurement approvals, stock adjustments and inter-facility transfers require authorised users.
7. **Privacy by minimisation.** Prefer aggregate service categories. Patient-identifying data is not required for core resource management.
8. **API-first, modular monolith.** Start with one FastAPI application divided into domain modules. Do not split into microservices prematurely.
9. **Frontend/backend contract stability.** API DTOs must map cleanly to the TypeScript domain and service interfaces in the frontend PRD.
10. **No false AI certainty.** Forecasts show data sufficiency, assumptions, confidence/uncertainty and a human-readable rationale.

## 3. Proposed technology baseline

Confirm versions and hosting only after inspecting the deployment environment and team constraints.

- Python 3.12+ (or the supported version selected by the team).
- FastAPI with Pydantic v2.
- SQLAlchemy 2.x ORM and Alembic migrations.
- PostgreSQL as the primary relational database.
- PostgreSQL row-level constraints and indexes; consider PostGIS only if geographic matching becomes a concrete requirement.
- Redis only when background jobs, distributed rate limits or caching justify it.
- Background jobs via a lightweight worker/queue when forecast generation, imports or notifications become asynchronous.
- Pytest, HTTPX TestClient, Ruff and mypy/pyright as appropriate.
- OpenAPI generated by FastAPI as the API contract.
- Object storage only for later documents/import artifacts; avoid storing patient records or unnecessary attachments.

Do not introduce a second database or microservice platform without a documented requirement.

## 5. Domain model

All tenant-owned records must carry an organisation scope directly or through a parent whose scope is validated. Use UUID primary keys. Use UTC timestamps in storage and ISO 8601 with timezone offsets in API responses.

### 5.1 Identity and organisation

- **User:** id, email, display_name, status, created_at, updated_at.
- **Organisation:** id, legal_name, organisation_type (hospital, clinic, pharmacy, laboratory, network operator), country_code, status.
- **Membership:** id, user_id, organisation_id, status, joined_at.
- **Facility:** id, organisation_id, name, facility_type, address fields, timezone, status.
- **FacilityMembership / RoleAssignment:** user, facility, role, granted_by, granted_at, revoked_at.
- **Location:** id, facility_id, parent_location_id, name, location_type (central_store, pharmacy, laboratory, ward, department, equipment_room, quarantine), status.

A user may belong to multiple organisations or facilities. Do not assume one user equals one facility.

### 5.2 Product catalogue and supplier

- **Product:** id, organisation_id or approved shared-catalogue reference, canonical_name, generic_name, brand_name, category, dosage/form where applicable, base_unit, unit_conversion metadata, product_code, barcode/GTIN if available, batch_tracking_required, expiry_tracking_required, active.
- **ProductAlias:** organisation_id, product_id, alias, source, verified_by.
- **Supplier:** id, organisation_id, name, contact fields, status.
- **SupplierProduct:** supplier_id, product_id, supplier_sku, quoted_unit_cost, lead_time_days, minimum_order_quantity, last_verified_at.

Product equivalence must not be inferred from fuzzy name similarity. Use trusted identifiers and authorised review. Pack/unit conversions must be explicit and validated.

### 5.3 Procurement and receipt

- **PurchaseOrder:** id, organisation_id, facility_id, supplier_id, reference, status, ordered_at, expected_at, created_by, approved_by.
- **PurchaseOrderLine:** purchase_order_id, product_id, ordered_quantity, unit, unit_cost.
- **GoodsReceipt:** id, facility_id, purchase_order_id nullable, receipt_reference, received_at, received_by, status.
- **GoodsReceiptLine:** receipt_id, product_id, quantity_received, unit, unit_cost, batch_id or batch details.
- **SupplierInvoiceReference:** optional reference/amount/date; do not implement payments in the first backend slice.

A purchase order does not increase stock. Stock increases only when a goods receipt is confirmed. The receipt must create stock ledger events in the same database transaction.

### 5.4 Batch and stock ledger

- **StockBatch:** id, facility_id, product_id, batch_number, expiry_date nullable only where policy allows, received_at, supplier_id nullable, quality_status (usable, quarantined, recalled, expired, damaged), unit_cost, source_receipt_line_id.
- **StockMovement:** id, organisation_id, facility_id, product_id, batch_id nullable only for non-batch-tracked products, movement_type, quantity, unit, source_location_id, destination_location_id, occurred_at, recorded_at, actor_user_id, reason_code, reference_type, reference_id, idempotency_key.
- **StockBalanceProjection:** optional derived/cache table keyed by facility, location, product and batch. It must be rebuildable from the ledger.
- **StockCount / StockCountLine:** physical count session and counted quantities, with variance posted as an adjustment event.

Movement types must include at least:
- RECEIPT
- INTERNAL_TRANSFER_OUT / INTERNAL_TRANSFER_IN (or a single transfer parent with two ledger legs)
- ISSUE_TO_DEPARTMENT
- CONSUMPTION
- RETURN_TO_STORE
- WASTAGE
- EXPIRY_WRITE_OFF
- DAMAGE_WRITE_OFF
- RECALL_QUARANTINE
- STOCK_ADJUSTMENT_IN / STOCK_ADJUSTMENT_OUT
- EXTERNAL_TRANSFER_OUT / EXTERNAL_TRANSFER_IN (later network phase)

Use decimal quantities where fractional units are legitimate. Store money as integer minor units plus ISO currency code, or an exact decimal strategy; never use binary floating point for money.

### 5.5 Equipment assets

Equipment is not consumable inventory and must not be mixed into drug/reagent usage calculations.

- **EquipmentAsset:** id, facility_id, asset_tag, serial_number, name, category, manufacturer, model, acquired_at, acquisition_cost, currency, condition, operational_status, current_location_id, warranty_end, maintenance_due_at.
- **EquipmentAssignment:** asset_id, location_id, assigned_to_label/user_id where permitted, assigned_at, returned_at, condition_out, condition_in.
- **EquipmentMaintenance:** asset_id, maintenance_type, description, performed_at, performed_by, cost, next_due_at, status.

### 5.6 Aggregate service categories

- **ServiceCategory:** id, organisation_id or controlled taxonomy reference, code, label, parent_id, active.
- **ServiceActivityAggregate:** id, facility_id, service_category_id, period_start, period_end, activity_count, source_system, imported_at.

This is optional and should contain aggregate counts, not patient-level records. Do not infer disease prevalence from medicine consumption. A medicine can be used for multiple indications. Disease/service trends are only defensible when an explicit, appropriately governed category is supplied.

### 5.7 Resource network

Later phase entities:
- **NetworkParticipation:** organisation/facility, visibility settings, agreement status, approved product categories.
- **ResourceNeed:** facility_id, product_id, requested_quantity, unit, needed_by, priority, status, created_by.
- **SurplusOffer:** facility_id, product_id, batch_id, available_quantity, expiry_date, storage/handling metadata, status.
- **TransferRequest:** sender_facility_id, receiver_facility_id, product_id, batch_id, quantity, proposed_terms, eligibility_snapshot, status, requested_by, approved_by.
- **TransferEvent:** transfer_request_id, event_type, actor, occurred_at, notes, evidence_reference.

Do not expose exact stock or sensitive procurement data to other organisations by default. Network visibility must be opt-in and policy-controlled.

## 6. Critical inventory invariants

These are non-negotiable domain rules and must be tested.

1. A confirmed receipt increases stock at exactly one destination location.
2. An internal transfer decreases the source and increases the destination by the same quantity, atomically.
3. An issue to a department changes location, not total facility stock.
4. Consumption reduces usable stock and is counted as consumption.
5. A return increases the destination balance only if the returned quantity is confirmed usable.
6. Wastage, expiry, damage and recall quarantine reduce available/usable stock and are separately reported.
7. A quarantined, recalled, expired or damaged batch is excluded from available stock and all transfer recommendations.
8. No movement may create a negative usable balance unless an explicit, separately authorised exceptional workflow is approved; default behaviour is reject.
9. A duplicate idempotency key for the same actor/action must not post a second movement.
10. A correction is a new compensating movement with reason and actor, not an edit/delete of historical ledger events.
11. Equipment assignment/checkout does not create a drug stock movement.
12. Every stock mutation is auditable and transactionally consistent.

All paired movements and their audit events must commit or roll back together.

## 7. API conventions

Base path: `/api/v1`. JSON request/response bodies. Use UUIDs. Use ISO 8601 timezone-aware timestamps. Paginate collection endpoints with `limit` and opaque or stable `cursor` (or page/limit for the first release, consistently). Include request correlation IDs.

Standard error shape:

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "The selected location does not have enough usable stock.",
    "details": {"available_quantity": "12", "requested_quantity": "15"},
    "request_id": "..."
  }
}
```

Use correct HTTP status codes: 400 invalid request, 401 unauthenticated, 403 unauthorised, 404 absent or inaccessible resource, 409 business conflict, 422 schema/domain validation, 429 rate limit, 500 unexpected server error.

## 8. Authentication, authorisation and tenant isolation

Production identity implementation is a separate security-sensitive workstream and must be reviewed before launch.

Requirements:
- Passwords must be hashed using a modern password hashing algorithm if password authentication is used.
- Prefer secure, HttpOnly, Secure, SameSite cookies for browser sessions where architecture permits; define CSRF protections for cookie-authenticated state-changing requests.
- If bearer tokens are used, define short access-token lifetime, refresh rotation, revocation and secure storage strategy.
- Enforce organisation, facility and role permissions on every endpoint and every object lookup.
- Never trust organisation_id, facility_id, role or actor_id sent by the browser without resolving the user's active membership server-side.
- Deny by default. Validate that source and destination facilities both belong to an authorised transfer context.
- Log role grants, revocations, login security events and sensitive inventory actions.
- Apply rate limits to authentication and externally exposed endpoints.
- Do not expose secrets in logs or error messages.
- Add security tests for cross-tenant IDOR, role escalation and facility boundary bypass.

Proposed initial roles: organisation owner, facility administrator, inventory officer, pharmacist, laboratory officer, procurement officer, equipment officer, auditor and network coordinator. Define permissions as explicit action/resource policies, not scattered role-name checks.

## 9. Analytics and forecasting

### 9.1 Source-of-truth event definitions

- **Purchased:** order quantity/value; does not mean received or consumed.
- **Received:** confirmed goods receipt.
- **Issued:** moved from central store to a department/location.
- **Consumed:** explicitly recorded use.
- **Returned:** usable quantity returned to a store.
- **Wasted:** discarded/damaged/contaminated quantity.
- **Expired:** quantity written off because expiry passed.
- **On-hand:** physical ledger balance by location and batch.
- **Available:** on-hand less reserved, quarantined, recalled, expired and otherwise unavailable quantities.

Reports must keep these measures separate. Do not label purchase quantity as usage.

### 9.2 Minimum analytics

- Current usable stock by product, batch and location.
- Consumption over time and top consumed products.
- Receipt vs consumption trends.
- Stockout incidents/days where historical data supports it.
- Expiring soon and expired quantity/value.
- Wastage by reason and product category.
- Procurement spend by supplier/category/period.
- Equipment register and utilisation/maintenance status (only where usage events are recorded).
- Service/diagnosis category counts from explicit aggregate records.

All reports must state period, unit, facility scope and data completeness. Drill-down should link to source ledger events.

### 9.3 Recommendation engine progression

Start with deterministic, explainable rules before introducing ML:
- Reorder point = estimated average daily consumption × supplier lead time + safety stock.
- Suggested reorder quantity considers current usable stock, outstanding confirmed receipts, expected demand during lead time, pack size and minimum order quantity.
- Expiry risk estimates whether expected consumption before expiry is lower than usable batch quantity.
- Seasonal patterns require multiple comparable periods and should be labelled insufficient-data when history is sparse.
- Network match requires same verified product identity, compatible units, valid batch status, remaining shelf-life policy, storage requirements and approvals.

Forecasting model choices (moving average, exponential smoothing, seasonal naive, gradient boosting, etc.) should be evaluated against a simple baseline using time-based validation. Never train/test randomly across time. Display forecast horizon, historical window, error metric and limitations.

LLM usage, if introduced, is for natural-language explanation and query assistance over authorised structured results. The LLM must not invent stock values, make clinical recommendations or execute procurement/transfer actions. Tool calls must be read-only by default; approvals remain explicit user actions.

## 10. Resource exchange safety and workflow

This is a later release, not the first backend vertical slice.

Eligibility should consider:
- Verified sender and receiver organisations.
- Exact product identity and permitted product category.
- Batch, expiry, recall and quality status.
- Remaining shelf life at estimated arrival.
- Storage/temperature/handling requirements.
- Pack/unit compatibility and legal transfer restrictions.
- Quantity available after sender safety stock.
- Transport route, cost and chain-of-custody.
- Explicit sender and receiver approvals.

Suggested state machine:
`DRAFT → SUBMITTED → MATCHED → SENDER_APPROVED → RECEIVER_APPROVED → DISPATCHED → RECEIVED → CLOSED`

Allow `REJECTED`, `CANCELLED`, `EXPIRED` and `DISPUTED` transitions with reasons. Do not allow state skipping. Dispatch and receipt events must capture actor, timestamp, quantity and batch identity. The system recommends and coordinates; it does not silently move stock or change ownership.

## 11. Privacy and regulatory readiness

- Data minimisation and purpose limitation.
- Aggregate service data by default; no patient-level records required for the core product.
- Define lawful basis, retention and deletion rules for each launch jurisdiction.
- Encryption in transit and at rest.
- Secrets management and rotation.
- Audit logs with access controls and retention policy.
- Data export and account/organisation offboarding.
- Backups and tested restoration.
- Document incident response and breach escalation.
- Conduct a privacy and security review before real facility data is onboarded.
- Determine local requirements for medicines, pharmacy practice, medical devices, controlled substances, product traceability and inter-facility transfers before enabling network exchange.

Do not claim compliance certification until a formal assessment has been completed.

## 12. Observability and operational requirements

- Structured logs with request_id, route, status, duration and safe actor/tenant context.
- Never log passwords, tokens, secrets or patient-identifying data.
- Metrics for request latency, error rates, database pool, job failures and queue depth.
- Health endpoints: liveness and readiness; readiness checks required dependencies.
- Database migrations are version-controlled and tested against a disposable test database.
- Backups, restore drills, retention and recovery objectives are defined before production.
- Background jobs must be idempotent and retry-safe.
- Alert on repeated failures, suspicious auth activity and reconciliation mismatches.

## 13. Testing requirements

### Domain tests
- Receipt posts the expected quantity.
- Purchase order alone does not change stock.
- Internal transfer is balanced and atomic.
- Issue is not counted as consumption.
- Consumption decreases stock and increments consumption analytics.
- Returns, wastage, expiry and adjustments reconcile.
- Expired/quarantined/recalled stock is excluded from available balance and network matching.
- Negative stock is rejected.
- Duplicate idempotency key does not double-post.
- Corrections are compensating events.
- Equipment is excluded from consumable totals.
- Service-category analytics require explicit category records.

### API/security tests
- Unauthenticated requests rejected.
- User cannot access another organisation's records.
- User cannot access an unauthorised facility.
- Role permissions are enforced for reads and writes.
- Client-supplied tenant/actor identity is ignored or validated against session.
- Invalid UUID, enum, quantity, unit, currency and date inputs rejected.
- Cross-facility transfers require explicit permission and valid workflow state.
- Error responses do not leak internals.

### Integration tests
- Receipt writes receipt, batch, movement and audit records atomically.
- A failed movement rolls back the whole operation.
- Database constraints protect uniqueness and referential integrity.
- Migrations upgrade from an empty database and from the previous migration.
- Analytics reconcile to ledger source events.

## 14. Delivery phases

### Backend Phase 0 — contract and foundation
- Confirm frontend domain types and service contracts.
- Confirm product catalogue ownership and organisation/facility model.
- Set up FastAPI app, configuration, database session, migrations, error handling and OpenAPI conventions.
- Add test database and CI checks.
- No production deployment until security basics are reviewed.

**Exit:** app boots, database migration runs, health endpoint works, API conventions are documented.

### Backend Phase 1 — identity and organisation foundation
- Users, organisations, memberships, facilities, roles and locations.
- Authentication and server-side permission policy.
- Audit events for identity and configuration changes.

**Exit:** authorised user can only access assigned organisation/facility resources.

### Backend Phase 2 — catalogue and inventory ledger
- Product catalogue, suppliers, purchase orders, goods receipts.
- Batch and expiry model.
- Inventory balances and movement history.
- Internal issue, consumption, return, wastage, expiry and adjustment.
- Idempotency and transaction safety.

**Exit:** full inventory workflow reconciles and is covered by domain/API tests.

### Backend Phase 3 — equipment and analytics
- Equipment asset register, assignment and maintenance.
- Consumption, procurement, expiry and wastage analytics.
- Explicit aggregate service-category reporting.

**Exit:** reports reconcile to ledger and asset data.

### Backend Phase 4 — recommendations
- Reorder and expiry rules.
- Forecast baseline and data sufficiency checks.
- Explainable recommendation review/approval.

**Exit:** every recommendation shows source data and rationale; no automatic procurement.

### Backend Phase 5 — network exchange
- Organisation verification and network participation.
- Surplus offers and resource needs.
- Match eligibility, approvals, transfer state machine and audit trail.

**Exit:** end-to-end test transfer between two test facilities with traceability and no unsafe product eligibility.

### Backend Phase 6 — integrations and scale
- Imports/exports and mapping.
- Approved HIS, pharmacy, laboratory and supplier integrations.
- Background jobs, monitoring, backup and resilience.
- Jurisdiction-specific privacy and regulatory review.

**Exit:** pilot integration and operational readiness review completed.

## 15. Frontend integration contract

The frontend must not be rewritten when the backend arrives.

- Keep UI dependent on feature service interfaces, not Dexie or raw API clients.
- Implement a local adapter for the demo and an HTTP adapter for production.
- Keep DTO-to-domain mapping in one boundary layer.
- Define loading, empty, error, retry and conflict states.
- Use server responses as authoritative for stock balances after integration.
- Handle optimistic updates carefully; never show a stock mutation as final until the server confirms it.
- Use idempotency keys for retryable stock-changing requests.
- Provide an export/migration plan for local demo data only if the product lead wants to preserve demo records; never merge synthetic records into production data.

## 17. Explicit exclusions until separately approved

- Diagnosis, triage, prescribing or treatment recommendations.
- Patient record/EMR replacement.
- Automated purchasing, payment, dispensing or stock transfer.
- Controlled medicines, vaccines, blood products, cold-chain items and other regulated/high-risk exchange categories without formal eligibility policy.
- Live third-party integrations before credentials, contracts and data governance are approved.
- Microservices before there is a demonstrated need.
- Claims of regulatory compliance or quantified environmental impact without evidence.

---

**Implementation rule:** Build the backend in vertical slices. The first useful slice should be organisation/facility-scoped product catalogue → goods receipt → stock ledger → inventory balance. Do not start with AI, the marketplace or a broad collection of empty CRUD endpoints.
